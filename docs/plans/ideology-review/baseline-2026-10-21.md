## 6. 第 6 步「影子权威 parity」：根因与结论（2026-10-22）

### 6.1 症状复现

`tests/probes/_probe_ideology_parity.gd`，`662ad422` + 当时工作树上自建 DLL：

```
final ideology parity: compared=1 matched=0 mismatch_day=2 field=points
```

与报告完全一致。`compared_count=1` 使 review 门槛「能比对」成立，但第 2 天起必然
不等，且第一个不同的业务段是 `points`。

### 6.2 先做的事：把 `points` 段拆成三份

`ideology_business_sections()` 的 `points` 原本把三个量混在一个哈希里：

```
points = mix(handle, ideology_points_q16, lifetime_points_q16, points_revision)
```

拆成 `points_balance` / `points_lifetime` / `points_revision` 三个**不参与总值**的
子哈希后，一次 build 就把范围缩掉一半：

```
field=points_revision          # 而不是 points
```

**这一步很值**：它证明 `ideology_points_q16` 与 `lifetime_points_q16` 两侧完全相同
（都是 0），分歧只在 `points_revision`。若继续按「A. 点数被累积两次」查
`accrue_points()` 的调用链，方向从一开始就是错的——累积两次会同时移动 balance 和
lifetime，而两者都没有动。

### 6.3 根因：参考快照是**空的**，不是数值不同

再加一个「首个差异国行」导出（`ideology_parity_points_diff`），拿到的是：

```json
{ "day": 2, "slot": 0,
  "reference_countries": 0, "worker_countries": 3,
  "reference_handle": 0, "worker_handle": 4294967296,
  "worker_revision": 1, "worker_baseline_population": 20 }
```

`reference_countries = 0`。**主线程这一天的参考快照一个国家行都没有**，worker 有 3 个。
于是「第一个不同的段」必然是 worker 有任何非默认值的段——`points` 只是因为
`points_revision` 从 0 变 1 而第一个撞上。

补充证据（同一份报告）：

```json
{ "reference_publish_count": 3, "reference_published_countries": 0,
  "reference_last_day": 2, "worker_committed_day": 2,
  "reference_catalog_hash": 4707967317838798614,
  "worker_catalog_hash": 4995997587266823155 }
```

参考**确实发布了**，带着 0 个国家行发布。而两侧 `catalog_hash` 本来就不同
（主线程用 `NativeIdeologyRuntime::compute_catalog_hash()` 的结果，worker 用
`RuntimeIdeologyPodAuthority::compute_catalog_hash()` 的结果），这一点被
`points = mix(business_seed(), state.catalog_hash)` 混进了 `points` 段，使
`points` 在任何情况下都不可能相等。

### 6.4 为什么主线程的国家行是 0

逐日探针（`accrue_result` = `accrue_points` 的早退原因码）：

```
day=1 suppressed=false accrue=2(economy revision 0) countries=0
day=2 suppressed=true  accrue=2                     countries=0
day=3 .. day=N         suppressed=true              countries=0
```

`suppressed=true` 来自 `run_ideology_daily` 的第一段：

```cpp
if (_runtime_host->domain_is_worker_authoritative(RuntimeDomainId::IDEOLOGY)) {
    out["ok"] = true; out["suppressed"] = true; return out;   // 不跑 accrue_points
}
```

第 2 天 worker 拿到全量授权（`authoritative_domain_mask=0xfff`），主线程当天起
**完全不跑 ideology daily**，因此 `accrue_points` 从未被调用，`_countries` 保持空。
而参考发布点就在这段 return **之后**——旧代码于是每天把空快照存进
`_ideology_references[day]`。

**与两个待验证假设的关系**：

| 假设 | 判断 |
|---|---|
| A. 点数被累积两次 | **不成立**。若成立，balance 与 lifetime 会一起移动；实测两者两侧都是 0。 |
| B. 账本输入不同（主线程经济快照 vs 冻结意见快照） | **不是本症状的主因**。两侧 `class_hash`/`class_count` 相同，`accrue` 走到的是「revision 0 / 已 suppressed」而不是输入形状不符。 |
| 实际根因 | 主线程在 worker 权威下被 suppress，参考仍是空快照却被当作有效参考；且 `points` 段混入了两侧本就不同的 `catalog_hash`。 |

### 6.5 本轮改了什么

| # | 文件 | 改动 |
|---|---|---|
| 1 | `runtime_ideology_pod.{h,cpp}` | `IdeologyBusinessSections` 增加 `points_balance` / `points_lifetime` / `points_revision` 三个子哈希（不参与总值），用于定位 |
| 2 | `native_simulation_host.cpp` | `publish_ideology_reference()` 拒绝零国家行的空参考并计数（`_ideology_reference_skipped_count` + 原因串），不再把空快照当有效参考 |
| 3 | `native_simulation_host.cpp` | 参考哈希改为**复用 `ideology_business_hash(reference)`**。旧实现手工重拼六个段且**漏掉了 `committed_day`**，两侧混入方式不同 |
| 4 | `native_simulation_host.{h,cpp}`, `runtime_pod_protocol.h`, `world_ext_runtime_graph.cpp` | 新增 `ideology_parity_points_diff`（首个差异国行的原始数值）与参考发布台账（`reference_publish_count` / `published_countries` / `skipped_count` / `skip_reason`），**无条件导出** |

### 6.7 尚未达成的验收项（必须登记）

06 §6 第 6 步的原始验收是 `compared_count > 0` **且** `matched_count == compared_count`。
本轮**只达成后者**，前者仍是 0。原因是结构性的，不是漏改：

1. `IDEOLOGY` 被授予 worker 时，`run_ideology_daily` 直接 return，
   **主线程当天不产生任何业务状态**，没有可比的一侧。
2. 不授予 `IDEOLOGY` 时，worker 的 stage 链在 `climate_authority_requested &&
   !active_climate_ok` 处整体 park；实测 `climate_trace_consumed=0`、`worker_day=1`
   恒定，worker 的 Ideology stage 一次也不跑（`ideology_pod_snapshot_generation=0`）。
   即使 `0xfff & ~0x10` 这种「只把 IDEOLOGY 留给主线程」的掩码也一样。

**因此单世界双权威在同一天比对，在当前 runtime 下不存在可行配置。**
测试因此写成蕴含式：*凡是发生过的比对必须相等*，并把「比对次数为 0」作为已知
待办登记在此，而不是用弱断言掩盖。

要从 0 变成 >0，需要以下之一（按代价排序）：

| 方案 | 代价 | 说明 |
|---|---|---|
| A. 双世界：同一构型各建一次，A 主线程权威 / B worker 权威，比业务哈希 | 中 | **已降级为退路**。实测两侧 Economy 节奏不同（主 `rev=10` / worker `rev=13`；主 `points=[0,22805,62227]` vs worker `[47023,46006,45706]`），比的是两个节奏不同的世界，不能当 parity 证据 |
| B. 给 HEADLESS 补确定性 Climate trace fixture | 大 | 05 §2.1 已登记；补上后 ACTIVE 路径才拿得到域授权 |
| C. 在 host 上开一个「SHADOW 下也跑 Ideology stage」的测试缝 | 小但侵入 | 会改动 authority 语义，需 review |

推荐 A：它比「同一帧两权威」更接近 06 §4「同一种子跑两遍」的原意，且不需要伪造
Climate。

### 6.7f 上面 6.7 的结论作废（2026-10-22 二轮实测）

**「单世界双权威不可行」是错的。** 上一轮那三条理由单独看都成立，但漏掉了
`runtime_country_parity_test.gd` 早就在用的第四种组合：

- `runtime_climate_authority_enabled = false` + `runtime_parity_forcing = true`
- **不碰授权掩码**
- **单步推进 worker 时钟**（`set_runtime_clock(false, ...)` + 等 `climate_trace` 前进）

机械原因：该模式下 worker 的 Climate 走 `commit_day_forced`
（`native_simulation_host.cpp:10903`），`climate_ok` 为真；紧随其后的 G7 SHADOW
Ideology 阶段（`native_simulation_host.cpp:10934`）因此**每天执行**；同时 `IDEOLOGY`
不归 worker，主线程 `run_ideology_daily` **不被 suppress**。这正是要找的
「同一世界、同一天、两种权威」。

上一轮没找到，是因为自己的探针开了 climate authority、掩码设成 `0xFFF & ~0x10`、
时钟常开——**没有照搬已知可行的驱动**。

照搬后实测（`tests/probes/_probe_ideology_shadow_driver.gd`）：

```
t=7  mask=0x0 pod_gen=1  cmp=0
t=18 mask=0x0 pod_gen=7  cmp=1  matched=1
t=28 mask=0x0 pod_gen=17 cmp=11 matched=11
FINAL compared=11 matched=11 mismatch_day=-1 field=
```

`compared` 从 0 变成 11 且全部相等。

### 6.7g 拆掉三处「两侧天生不同」的字段

照搬驱动后仍先报 `field=points` → `points_revision`。逐层拆开，全部是同一类错误：
**把两侧按构造就不同的量混进了业务哈希。**

| 字段 | 为什么两侧天生不同 | 处理 |
|---|---|---|
| `catalog_hash` | 两侧用两个不同函数算（`NativeIdeologyRuntime::compute_catalog_hash()` vs `RuntimeIdeologyPodAuthority::compute_catalog_hash()`） | 移出 `points` 段；改为独立门槛 `ideology_parity_catalog_mismatch_count`，只报告不计 mismatch |
| `points_revision` | `row->points_revision = opinion.revision`，存的是**外部 Economy 发布编号** | 移出 `points` 段，保留为 `points_revision` 诊断子哈希 |
| `history_count`/`history_head` | 环形缓冲游标，记录"写了多少次" | `history` 段只混**非零**增益；游标移入 `history_cursor` 诊断子哈希 |
| `rng_state` | 种子是 `handle ^ (catalog_hash + 常量)`，两侧 catalog_hash 不同 | 新增共享 `RUNTIME_IDEOLOGY_RNG_SEED_MIX` + `runtime_ideology_country_rng_seed(handle)`，两侧同源 |

另有两处是**时序**而非字段：

1. **参考帧只在结算完成时发布**：`run_daily` 分片，`done=false` 时发布的半成品会被
   worker 拿全天状态去比 → 必错。现在要求 `done && last_day == day &&
   points_accrual_ever_settled()`。
2. **发布 opinion 前先让主线程结算到同一 revision**：否则 worker 会从主线程"还没看到"
   的输入累积（实测 worker 看到 10 栋建筑、主线程 9 栋，worker 多赚 23002 点）。
   现在发布前调 `settle_points_for_opinion(revision)`（按 revision 幂等，不会重复计）。

### 6.7i 第二轮续查：找到并修掉一处，但暴露出架构层根因

**先纠正上一轮 6.7i 的读法。** 上一轮把 `settled_now=false` 当成「accrue 走了已见过短路」，
这是误读：`settle_points_for_opinion` 在 `_points_revision_seen == revision` 时**故意**返回
false（已对齐＝不需要再结算）。据此继续追是错的。

#### 修掉的一处（真实、有效）

**主线程不得在 worker 启动之前先结算。**

`accrue_points` 给每个国家设一个**高水位基线**，取「第一次观测到的值」，且只升不降。
所以**谁先结算，谁定自己的起点**。原来的驱动让主线程在 revision 1 就先结算（基线取到
9 栋建筑），worker 到 revision 3 才起步（基线 10 栋），主线程那次「追赶」永远还不回来。

修法：worker 尚未起步（`ideology_pod_snapshot_generation == 0`）时不跑主线程当天。

效果：`matched` 从 **5 → 8**（`first_mismatch_day` 从 2 → 12）。但这不足以转绿，见下。

另修：参考帧改在 `run_daily` 走完且 `last_day == day` 时发布，避免分片半成品被拿去比。

#### 架构层根因：两侧 Economy 推进速度不同

用加进报告的 `ideology_parity_worker_opinion_revision` 直接量到：

```
worker_opinion_rev=13   主线程 ref_points_rev≈2
```

- **worker 的 Economy 由 worker 自己时钟驱动**（`execute_economy_worker_stage`），
  驱动循环里每 step 一次 worker 就往前走一个经济日；
- **主线程 Economy 是协作分片**，`run_daily_tick` 每个 driver tick 只推进那么多。

于是 worker 消费到 economy revision 13 时，主线程才到 2 附近。`accrue_points` 按
「每次 revision 结算一次」设计，两侧结算次数不同 → `points_revision`（外部编号）、
`history` 游标、以及**基线取样时刻**全都不同。

这不是调用顺序能解决的：**两侧 Economy 的时间轴本身就不同步**。

#### 结论：同一个 Economy 实例，两侧读到的 revision 序号不同

先排除了一个看起来最合理的猜测：worker 用的是**另一套 Economy 实例**。不是。
`world_ext_simulation_host.cpp:719-729` 里 `attach_economy_production_runtime(economy)` 传的
就是主线程的 `_economy_runtime` 同一个指针。`_class_opinion_revision` 是共享计数。

所以两侧读到不同编号，只能是**读取时刻不同**。逐 tick 观测证实了这一点：

```
[pub 3]  ok=true rev=1 main_seen=1      <- day 3：主线程与参考都在 revision 1
[pub 6]  ok=true rev=4 main_seen=4
[pub 14] ok=true rev=10 main_seen=10    <- 主线程一路同步，没有滞后
```

主线程的 `main_seen` 与 `econ_rev` **逐 tick 完全同步**（1→10），健康。
而 worker 在 day 3 那天是用 **revision 4** 结算的——它在 driver tick 之内又多推进了
2 个 revision。`execute_economy_worker_stage` 只在 (day, input_generation) 变化时执行，
但一次 worker step 可能跨过多个 input generation。

`accrue_points` 的语义是「每个 revision 结算一次」并据此维护高水位基线，于是：
同一日历日、两侧不同的 revision 编号 → 基线取样点不同 → 点数累积不同。
`points_revision` 与 `history` 游标随之不同（这两个已从业务哈希移出，但 `baseline`
差异是真的）。

这**不是**调用顺序或字段污染能修的：它是「两侧经济时间轴与日历日的耦合方式不同」。

#### 下一轮的正确入口

`execute_economy_worker_stage`（`native_simulation_host.cpp:2389`）+ 调用它的 stage 循环
（`native_simulation_host.cpp:11317`）。需要让 worker 在一个日历日内**至多推进一个
revision**，与主线程 `run_ideology_daily` 的日节拍一致；或让主线程在一个日历日内
推进到与 worker 相同的 revision 次数。前者更符合 parity 原意。

本轮试过「按 revision 号把主线程往前推」的做法（在 driver 循环里循环调用
`run_economy_slice` 直到追上 `worker_opinion_revision`），实测无效：`matched` 在
5 / 8 / 9 之间浮动，因为 worker 的 revision 在同一个 tick 内还在继续涨，追不上。

**本轮不宣称 parity 达成。** 门禁保持红色。

#### 另需登记的观测事实

`matched` 会在 **5 与 8 之间浮动**（同一 DLL、同一命令，连跑 4 次出 5，另一次出 8）。
同一个业务逻辑错不会浮动，所以这本身就证明残余分歧是**时序竞争**。
本轮门禁因此**保持红色**，并且只断言「`compared > 0`」与「`matched == compared`」，
不把任何浮动值写死成期望。

### 6.7j 第四轮：修掉五处真实缺陷，其中两处是上一轮自己引入的生产泄漏

#### 撤回：上一轮的「时序修补」不该进生产（P1）

`world_ext_ideology.cpp:225` 无条件调用 `settle_points_for_opinion()`。它的生产调用点有
`world_ext_runtime_graph.cpp:473`（每次 graph pulse）、`:375`、`world_ext_ideology.cpp:458`、
`world_ext_country.cpp:1051`——也就是说**点数结算的时机和记账日期被测试需求改掉了**。

已处理：删除 `settle_points_for_opinion()` 及其调用，点数只由 `run_ideology_daily` 结算。
它也**没有**修好那处差异，见下。

#### 撤回：生产环境每天全量导出 reference（P1）

`world_ext_ideology.cpp:346` 只判 `_runtime_host != nullptr`，而生产里它必然存在 → 每天
导出 + 哈希一份完整快照，并保留 128 份（`native_simulation_host.cpp`）。

已处理：
- 新增独立开关 `set_runtime_ideology_parity_enabled(bool)`（默认 **false**），
  与 `climate_parity_forcing` 分开；
- `run_ideology_daily` 在 **export 之前**短路，不是先导出再让 publisher 拒绝；
- 保留深度 128 → **2**（day-keyed map）+ 16（配对队列）。

#### 修掉：`trade_q16` 是流量项，却按「每次结算」全额发放（真实业务缺陷）

这是「两侧点数真的不同」的根因，比时序重要：

```cpp
ledger.trade_q16 = mul_sat(trade_per_day, _point_trade_weight_q16) / TRADE_MONEY_SCALE;
```

`population_q16` / `building_q16` 是高水位**增量**（只付一次），但 `trade_q16` 是**每天
的流量**，每调用一次 `accrue_points` 就全额支付一次。两侧结算次数不同 → 总额必然不同。
实测：day 1 一侧 `points=0`、另一侧 `41290`。

修法：每行记录 `trade_paid_day`，**每天最多付一次**。两侧实现一致，字段进存档
（`runtime_ideology_pod.cpp` serialize/restore + `ideology_runtime.cpp` capture/restore）
与 `compute_state_hash`。修后主线程点数由 `0 → 46859`，不再是「一侧永远 0」。

#### 修掉：参考帧按错日历配对，把配对错误报成业务分歧（P1 级误报）

主线程按 driver tick（`day_index`）发布，worker 按自己的 `committed_day` 查找。
实测 `ref_day=14` 对 `worker_day=12`——**两个日历不同**，于是：

- 原代码按绝对日查找 → 几乎全 miss → `compared=0`；
- 我改成裸 FIFO → 把 day 14 配给 day 12 → `matched=0`，`first_mismatch_day=1`，
  看起来像「第 1 天业务就错」，实际是配对错。

修法：从待配对队列里取**日历距离最近**的那一帧。修后 `paired_ref=12` = `paired_worker=12`，
配对完全对齐。

#### 修掉：报告字段指错（P2）

`native_simulation_host.cpp` 先判 `points_revision`，但该字段**已不参与** `points` 哈希，
于是「点数 0 对 23002」却报 `field=points_revision`。

修法：只按真正参与 `points` 的 `points_balance` / `points_lifetime` 归因。
现在实测 `field=points_balance`，与事实相符。

另外新增「逐行复算」诊断 `ideology_parity_row_mismatch_slot/handle/reference_points/
worker_points`——段哈希是累计混合，只能靠逐行复算指出是哪一行，实测输出
`slot=0 ref_points=46859 worker_points=67969`。

#### 修掉：catalog 一致性检查形同虚设（P2）

两侧 `catalog_hash` 由两个不同函数算，比较它必然每天「不一致」。

修法：改成**就绪性**检查（任一侧为 0 才计数），不再比较两个不可比的值。

#### 修掉：抽卡种子与世界无关（P2）

`runtime_ideology_country_rng_seed` 只吃 `handle`，每局同国抽卡序列相同。

修法：加入 `world_seed`（splitmix 打散），经 `RuntimeIdeologyPodCatalog::world_seed`
两侧同源传递并纳入 worker catalog 哈希。`world_seed` 是可选 catalog 键，缺省 0 时
行为与以前一致（仍两侧一致，parity 不受影响）。

#### 修掉：`Invoke-RuntimeTests.ps1` 全部路径失效（P2，既有问题）

实测 `Test-Path`：改前 **4 存在 / 35 缺失**（所有条目写成 `tests/runtime_*.gd`，实际在
`tests/runtime/`）。已按文件名重建映射并整体重写，改后 **39/39 全部存在**。
这让「已登记进套件」这句话第一次真正成立。

#### 修掉：`worker_day` 是过期值（P3）

报告里没有 `ideology_worker_day` 字段，探针读到的是默认值，所以永远打印 `worker_day=1`。
新增真实的 `ideology_parity_worker_committed_day`（worker 最后提交的理念日）与
`paired_reference_day` / `paired_worker_day`。

#### 修掉：guard test 没有敏感性断言（P3）

新增：
- 发一条 `GRANT_POINTS` 命令后，`points` 与 `points_balance` **必须变化**；
- `ideas` / `bits` **必须不变**（分段独立）。

checks 从 16 → **21**。这让「各段一致」不再可能空过。

### 6.9 环境备注

- 构建：`gdext/` 下 `PYTHONPATH= VSLANG=1033 scons platform=windows
  target=template_debug dev_build=no -j8`，判据 `scons: done building targets.`
- 探针必须**不加** `--quit`：本文件用的是 `call_deferred` + `await process_frame`，
  `--quit` 会让 SceneTree 在断言前退出，表现为「只打印第一行 OK 就退出」。
- Godot 可执行文件是**目录** `D:\Godot\Godot_v4.6.2-stable_win64.exe\`，
  真正的程序在同名子目录内，需用 `..._console.exe`。
- `host.runtime_climate_authority_enabled = false` **不会**让 worker 停摆——上一轮这么写
  是错的。它让 worker 走 `commit_day_forced`，`climate_ok` 依然为真，worker 照常推进。
  真正会停摆的是 `runtime_parity_forcing = false`（没有 forced climate commit）。
