# 开发指南：新增系统、功能与维护

先读 [世界运行架构](world-runtime-design.md)。本指南适用于新功能和既有模块迁移；目标是让下一位开发者能判断代码该放哪里、怎样接入、怎样证明没有破坏其他系统。

## 1. 先决定功能归属

| 要做的事情 | 放置位置 |
| --- | --- |
| 调整数值、目录和条件 | 现有模块内容目录 |
| 改已有计算规则 | 拥有该状态的业务模块 |
| 新增独立状态、生命周期和周期 | 新业务模块 |
| 新按钮、面板、地图效果 | 展示层与请求适配器 |
| 自动决策 | AI/应用层；提交普通命令 |
| 文件、账号、网络服务 | 平台服务 |
| 运行、暂停、保存、关闭规则 | 世界会话/模拟核心 |

仅仅增加一个按钮不需要新模块；已有模块开始保存另一套独立身份、周期和存档状态时，应考虑拆出模块。

## 2. 开工前写一份短契约

```text
模块：
负责的数据与单位：
接受的请求与回执：
只读依赖与采样时点：
推进频率、继续条件、提交点：
对外视图与事件：
保存片段、版本、恢复依赖：
暂停、关闭和重新执行的处理：
需要保持的业务规律：
```

设计要能回答：“同一请求收到两次怎么办”“执行一半退出怎么办”“其他模块尚未完成怎么办”“读旧存档怎么办”。答案应落实在已有协议或测试中，不能只写注释。

## 3. 建议的模块内部结构

```text
module/
  contract       输入、命令、回执、只读结果
  state          唯一可写状态与稳定身份
  rules          不依赖界面或线程的计算规则
  runtime        周期、阶段、游标、提交
  persistence    本模块保存与恢复
  adapter        与模拟核心、平台层的连接
  tests          业务规律与交接场景
```

这是职责划分，不要求每个小模块都建立七个文件。C++ 热循环避免 Godot 对象和逐项字典查询；脚本负责资源编译、粗粒度调用和展示。完整世界指针、总控私有字段、其他模块的可写容器都不是正常模块接口。

## 4. 完整例子：添加疾病系统

假设需要根据人口、交通和气候计算疾病影响。

1. `health` 拥有地区感染状态、传播进度、恢复记录。人口仍由经济模块拥有。
2. 启动时读取不可变疾病目录；每周期冻结已提交的人口、交通、气候视图及版本。
3. 病情按自己的周期计算，保存阶段和游标；工作未完成时返回继续条件。
4. 需要影响劳动能力时，向既有修正模块提交带编号的效果请求；需要减少人口时，向人口所有者提交明确业务命令。疾病模块不直接改人口数组。
5. 只有接到完成回执后，才把相关后果标记为已处理；重复唤醒沿用原编号。
6. 发布地区病情摘要供界面显示。界面关闭、过滤或排序不影响模拟。
7. 登记 `health` 的依赖、调用阶段、保存片段和版本；恢复顺序依赖人口与效果状态，而不是手工猜数组位置。
8. 提供禁用/缺失模块时的存档策略；不得静默丢弃已有病情。
9. 测试无病、暴发、零人口、重复请求、执行中暂停、保存恢复、关闭及同种子重复运行。

这个例子不要求现在实现疾病功能，目的是约束未来接入方式。外交、宗教和运输系统使用同样的登记与交接方法，不必复制疾病规则。

## 5. 请求、结果和错误

- 校验失败：明确拒绝，提供稳定原因；不能修改一半后返回失败。
- 已接受：返回请求编号，调用方继续等完成回执。
- 等待依赖：保存游标，声明等待什么；唤醒时重试同一操作。
- 已完成：发布唯一回执和已提交变化。
- 不可恢复错误：记录当时模块、阶段、日期和输入版本，关闭新的模拟工作。

不要用超时后自动成功、截断内容、跳过未完成结算来掩盖问题。性能预算只能决定何时让出执行，不能改变业务结果。

凡是会让后台等待主线程的请求，必须有不依赖“下一天”的继续入口。当前宿主的
`_service_runtime_liveness` 在日期无法继续提交时仍服务这些请求；未完成工作保留原日期，
完成后停止重试。不能只在日更新里登记等待，却要求日历继续前进才处理等待。
实例刷新与派生重建的实际例子见 `tests/runtime/ideology_day_continuation_test.gd`。

## 6. 状态和生命周期

数据归属独立于线程。停止后仍要读取最后真实状态；不能因为后台不再接受工作就回到旧主线程副本。交接时先停止新任务、结束当前调用，再明确转移状态。

父对象拥有子模块，子模块只借用必要接口；回调不得造成永久的互相持有。异步任务携带世界代次，结果安装前检查仍属于当前世界。取消需唤醒等待者，使它能正常退回，而非只把外层对象销毁。

图形资源也需明确所有者：`VisualTileHorizonBaker` 创建的本地 `RenderingDevice` 是需要
显式释放的对象。成功、失败、取消和对象销毁都走同一个清理入口；已经提交的 GPU 工作
先确认完成，再释放资源句柄和设备。仅将设备变量设为 `null` 不会销毁它。
这类问题必须用真实图形模式检查，无画面模式不会创建该设备。

当前入口是 `world_session.gd`。一局游戏对应一个实例，登记完成后锁定组合；
`prepare()` 按依赖执行，`request_close()` 立即关闭入口并通知取消，`close()` 等待
准备调用退出，再按相反顺序释放。`CLOSING` 与 `CLOSED` 有实际区别：释放失败时
保留拥有关系和错误，不能把失败写成已关闭；并发关闭请求共用同一次释放。

新增需要准备/释放的系统，在 `WorldRuntimeHost.generate_world()` 之前登记：

```gdscript
const SessionModule = preload("res://scripts/game/runtime_session_module.gd")
var adapter = SessionModule.new().configure(
    "health", PackedStringArray(["restore"]), PackedStringArray(["health.state"]),
    health.prepare, health.cancel, health.release)
var registered = host.register_session_module(adapter)
if not registered.ok:
    return registered
```

`prepare`、`release` 必须返回 `{"ok": true}` 或明确失败，可等待真正的完成信号；
`cancel` 必须同步阻止新工作并唤醒本模块的等待者，不能同步等待自己正在取消的调用。
准备到一半失败的模块仍会被释放。依赖对象由装配入口传入 `health`，回调不接收万能总控。
依赖可选 `world`、`presentation`、`restore` 或其他已登记模块；`simulation` 一定在
所有扩展准备完成后启动，并在它们释放之前停止，不能把扩展反向依赖到 `simulation`。
组合中缺依赖、重复数据归属或存在环时，登记不生效。

这些方法管理一局游戏的资源，不代替每日计算。环境计算接到
`gdext/src/system_schedule.{h,cpp}` 的原生计算图；已有经济/国家等功能接到其拥有者的
阶段和命令入口。后台扩展使用普通数据，不能从原生执行线程调用这里的 Godot 回调。
只有确实新增独立执行边界才修改 `runtime_pod_protocol.h` 的十二个执行域。

`session_report()` 提供代次、状态、模块和失败原因。延迟任务保留原会话及代次，
安装结果前检查 `is_current(token)`；不要读取“此刻的会话”来替旧任务通过检查。
`GameFlow` 在换场景/退出前等待 `close_world()`；关闭窗口走同一条退出流程。
已经冻结成字节的后台写盘归文件服务所有，退出程序等待写入结束。
测试示例见 `tests/game/world_session_test.gd` 和
`tests/runtime/runtime_worker_stop_lifetime_test.gd`，后者用真实世界验证新增模块的释放顺序。

## 7. 保存与版本

模块只能编码自己拥有的状态；共享状态由真实所有者保存。保存临时工作所需的业务游标和未完成请求身份，或明确要求在提交边界保存。禁止丢弃待办后伪造“干净”快照。

当前经济保存要求完整结算边界；旧 ECP2 resume 片段仅有游标，不能用于继续执行，明确拒绝导出和安装。
新增中途保存必须连同冻结输入、部分结果、待办事务及其身份一起版本化保存，并验证跨进程继续结果；
不得只保存阶段编号，或在缺少暂存数据时从头重放已经支付的操作。

格式版本、内容目录身份、执行规则身份分别比较。它们不能互相代替。恢复先验证，再安装；明确处理旧版本和可选片段。跨模块恢复依赖登记成图，重复名称、缺少依赖和环都应阻止启动。

当前保存扩展 API：在 `GameSave` 就绪后、绑定世界之前，创建
`RuntimeStateProvider`，用本模块的方法配置 `can_save`、`write_sections`、
`restore_sections` 和哈希回调，然后调用：

```gdscript
var result = GameSave.register_state_module(provider,
    PackedStringArray(["pkcn", "ecp2"]))
if not result.ok:
    return result
```

登记验证通过才安装新组合；已进入游戏时拒绝改动。扩展模块收到自己的原始字节，
自行解码，玩家展示在所有业务模块恢复后安装。可读旧版本通过
`provider.configure_compatibility(...)` 声明；未声明时只接收当前版本。
额外状态片段必须有唯一所有者。现有 18 个内建模块的装配位于
`scripts/game/world_state_modules.gd`，依赖解析位于 `runtime_module_registry.gd`。
完整例子和真实保存恢复验证分别见 `tests/game/fixtures/extension_state_module.gd`
与 `tests/game/game_save_roundtrip_test.gd`。

### 旧模块现已使用的接口边界

`save_modules/` 按地理、时间、模拟包、国家/军事/AI、经济、规则、视野、历史、玩家展示分组。
总计仍是 18 个独立登记的保存模块；分组只共享同类辅助方法，不合并片段身份或恢复依赖。
`world_state_modules.gd` 只组装，`world_state_bindings.gd` 只连接现有对象；
总控不再保存各模块的读写实现或解析分支。

- 用 `retain_adapter(adapter)` 明确让 provider 拥有适配器；适配器不能反向保存 provider。
- 用 `configure_context_binding(binding)` 在**每次调用**取得所需接口。恢复国家后经济接口可能重建，不能在登记时缓存旧 facade。绑定函数可认识宿主，返回值不得包含整个宿主或生成器。
- `configure_restore_reads(...)` 声明读取其他片段；恢复回调只收到自身片段和所声明的片段。它是数据依赖，不等于安装顺序：例如军事恢复读取保存的玩家身份，但玩家展示最后才安装。
- 用 `configure_codecs(...)` 声明字节或字典格式；复杂格式用模块自己的 `configure_decoder(...)`。解析发生在准备载入时，不能边解析边修改世界。新扩展也应在这里校验，避免把错误推迟到部分模块已经恢复之后。
- 可选旧片段的缺失策略由模块兼容声明决定；PKSR 接受原生包和明确版本的旧字典，不能拿通用 Variant 解码原生包。
- 保存的国家后续准备、经济目录重绑、视野恢复和玩家展示使用明确回调，不能在总控循环里新增 `if provider_id == ...`。

新的时间控制接入使用 `runtime_clock_binding.gd`：执行者建立之后 `attach`，先同步当前暂停和速度，之后订阅 `WorldClock.control_changed`；停止前 `detach`。
界面、剧情或保存只操作 `WorldClock`。修改暂停和速度时无需再手工调用主机同步，重复设置同一速度也能正确从暂停恢复；故障保持期间不能通过字段赋值绕过暂停。
原来的定时重发控制已移除，运行等待不能被当作需要强行恢复的暂停。

### 界面检查中的运行与阅读状态

剧情弹窗属于正式交互，会暂停时间并关闭国家面板。连续运行测试必须完成实际选择和结果确认，再重新打开面板；不能直接清锁或循环强制恢复时钟。
切章后等布局完成，再用 `max_value - page` 判断实际可滚动距离；非零阅读位置的检查应使用真正超出视口的内容。
隐藏面板会使 Godot 容器缩小并把滚动条归零，因此页面在隐藏前保存阅读位置，在重新显示并完成布局后恢复；迟到的恢复不能覆盖用户的新滚动。
小窗口财政页面将工具、采购及列表放在同一外层滚动区，避免固定头部把列表高度挤成零。
验证关闭面板是否改变暂停状态，应在按键调用前后核对，再单独等待关闭动画；不能拿几十天前的暂停状态作比较，或把动画期间新出现的剧情暂停归因于按键。
macOS 切换窗口模式时可能在自动加载节点尚未完成准备的调用中处理帧和延迟任务；
测试应等待最后的自动加载节点 `GameFlow` 准备完成，再创建玩家场景。
图形测试结束先等待 `close_world()`，再销毁玩家场景并退出；同时检查真实图形对象的泄漏日志。

## 8. 验证要覆盖什么

| 改动 | 必需证据 |
| --- | --- |
| 公式/内容 | 具体输入输出和业务规律 |
| 钱、物资、人口 | 总量核对，允许增减须有明确来源/去向 |
| 周期与调度 | 跨帧继续、依赖未就绪、同一天重试、不同运行速度 |
| 多模块事务 | 成功、拒绝、重复、在途停止、恢复后继续 |
| 保存 | 真正保存→载入→继续计算，含旧格式处理 |
| 生命周期 | 加载中关闭、运行中关闭、暂停后关闭、重启、零泄漏 |
| 并行路径 | 与同输入的单执行路径比较，重复运行检查顺序敏感问题 |
| 性能 | 相同地图、天数、模式下的实际耗时和内存；列明测量条件 |

不要把“程序没有崩溃”作为账目正确的证据，也不要把测到的空结果互相相等当作功能通过。测试等待真实回执或已提交版本，不能仅睡一段时间后假定完成。

`starter_settlement_soak_test.gd` 默认运行 3650 日，逐日核对账目，并在 60/730/3650 日读取快照。
无界面的模块测试也必须按当前数据归属推进：此测试通过 `WorldRuntimeHost.configure_session/generate_world` 创建正式世界，
沿现有 `headless_perf_record.gd` 的 `run_daily_tick/finish_daily_tick` 入口提交日期，再消费实际后台结果。
采用与 PlayerGame 一致的运行配置，时钟控制仍通过会话绑定传递，结束时调用 `close_world` 等待释放。
测试逐日投递以便核对每份账目；季节相位采用 `WorldClock.season_phase()` 的 0–4 约定。
它不触发年报界面，避免年末报告额外推进日期而跨过一次取样；年度报告的展示和交互应另行测试。
不能直接循环旧国家/经济任务来代替统一执行者，也不能用未来研究队列是否为空判断当天结算是否完成。

```sh
python3 tools/ci/run_regression_checks.py --godot /opt/homebrew/bin/godot \
  --log-dir /tmp/keynes-starter-soak tests/game/starter_settlement_soak_test.gd
```

## 9. 修改现有大文件

先确定一组完整职责，提取明确输入/输出后迁移；同次删除旧实现。只把类方法挪到不同文件能降低编译成本，但不代表数据归属已经拆开。

新功能不得默认继续扩展 MapGenerator、WorldRuntimeHost 或 NativeSimulationHost 的任意私有字段。确需修改装配入口时，留下注册和委托，业务规则放入所属模块。具体文件维护约定见 [模块边界](module-boundaries.md)。

### 当前可复用的经济接口例子

- 开局先在 `bootstrap/test_start_inputs.gd` 捕获普通数据，再交给规划和资金模块。
  计算过程中不得回查活动世界、内容注册表或 Facade；源对象改变或释放不能改变已捕获的计划。
  新增测试聚落的科技和建筑放在 `test_start_policy.gd`，科技标签按“满足任一个可选解锁”处理。
  正式玩家开局仍由 `StarterSettlementBootstrap` 负责，不以测试聚落策略替代。
- `EconomyAuthorityTransfer` 是经济状态与执行者/存档之间的窄入口。
  需要临时延后国家核验或使用已提交的国家身份时，作用域结束必须恢复原设置，失败也一样。
  不重新授予整个总控友元权限；诊断只能在 `EconomyInvariantProbe` 自己创建的对象上运行。
- `EconomyRecordSource` 只在模拟状态可读的边界采集；将普通字段写进 `Batch` 后交给写盘线程。
  写盘线程不能查询运行世界、保留运行对象或重新实现价格等业务公式。
  新增记录字段同时修改源字段、批次、CSV 表头/编码和列数检查；改变文件列布局才升级版本。
- 共同执行入口必须先更新观测日期，再按当天阶段采集和分批更新；切换调用方式不能使缓存使用前一天的分组。
- 投资评估由当前周期的到期列表决定。分片只保存本周期内的游标；不得再加一层跨周期的
  “分摊待办”，否则旧候选可能混入新价格与新资金。需要新的近似规则时必须设计缓存身份和失效规则。
- 载入后首次读取不能用浮点展示副本覆盖存档中的整数资源量。由上次观测推导的事件
  （例如降雨增加）要恢复上次观测，而不只是累计结果；检查保存后继续运行的完整状态一致性。

测试业务机制时，把必要的配方、需求、资金与岗位写在测试里。不能假定不断更新的正式内容
永远保留某项家庭消费、某一项建材位置或固定工资。先断言前提真实成立，再断言结果；
当检查人员换岗时，先证明来源岗位有人；当检查就业扩张时，确保存在可支付的商品需求。
资金、物资、人口、单线程/后台一致性和载入后继续运行的检查不得因此删除或放宽。

## 10. 文档和完成标准

功能交付同时更新模块契约、相关存档说明、登记表及验证证据。报告需要清楚区分：目标设计、实际接入、已验证平台、未完成事项。只运行 macOS 无画面测试时，不得写成所有平台和真实界面均已通过。

未来开发的最低完成标准：功能可用、归属明确、交接可恢复、已有结果未意外改变、没有新增资源泄漏、下一个开发者能从登记和契约找到扩展位置。

构建与带墙钟故障检查的运行测试分开执行。经济重启场景保留既有 5 秒 peer 等待门槛；
并行编译造成的争用也可能触发它。出现失败应保留原日志，排除争用后复核，并检查是否
真的丢失回应；不得删除断言、扩大超时或只留下成功的一轮来宣称稳定性。

默认检查器已纳入本轮修复的建筑、测试开局、物资、周期、执行一致性与经济存档检查，共 31 个脚本；
`--roundtrip` 另跑真实开局保存载入。GitHub Actions 使用同一个默认清单，不能只跑少量会话检查而漏掉已修复的领域规则。
3650 日运行与真实图形检查单独执行，避免把无画面通过等同于全部验收。

当前改造的证据和已知限制见 [接入与验证记录](world-runtime-validation.md)。
