## 性能复查：修掉自己引入的两处复杂度问题

用户问「目前的做法会不会有性能风险」。逐条复查后确认：

**今天的实际风险 ≈ 0**——最贵的那条路径（非 SUM 聚合）**一次都没跑过**：
全库 `grep "aggregate_policy = [1-9]"` = **0 条**，`source_cap` 也是 0 条。
所以 L1-6 的新分支目前是死代码。

但复查发现两处写法有真实复杂度问题，已修（重编 + 回归绿）：

### 1. `ModifierRuntime::rebuild_bucket` 的来源分组

原写法：每个 member 线性扫 `by_source` 找同一个来源 → **O(m · s)**。
200 个来源的格域桶 = 4 万次比较/重建。
改为：先全部 `emplace_back`，循环结束后按 identity 排序 + 折叠相邻（`by_source.resize(merged)`）
→ **O(m log m)**。

### 2. `NativeIdeologyRuntime::collect_effect_activations` 的倍率解析

原写法：`magnitude_scale_for(country, program)` 放在「目标 × 层」**双重循环内部**，
32 格 × 3 层 = 同一答案算 96 次，每次扫全部协同。
改为：提到循环外，`activation_scale_q16` 算一次。

验证：`runtime/runtime_modifier_pod_test` 13/0（覆盖 SUM/MAX/TOP1/TOP2 =
0.5/0.25/0.25/0.5）、`ideology/ideology_effect_scale_override_test` 20/0、
`ideology/ideology_effect_instance_test` 51/0。

### 仍存在、但现在不该修的一条

非 SUM 的桶在**每次 add/remove 时全量重建**（O(m)），n 次变更就是 O(n²)。
今天无 stat 启用所以是 0 成本；若将来有热门宽 stat 用 TOP_N，正解是增量维护
top-N（小顶堆），不是现在做——现在做等于为不存在的数据结构付复杂度。

### 其它项的成本结论

- A 第二段倍率：每实例多 1 个 int32 列 + 触发时 1 次乘法（scale==1.0 走原路径，
  逐位不变）；存档每实例 +4 字节。
- L4-11 保底：抽卡时复制一份池 O(n)，n≈180，玩家手动触发。
- C1 日志：`vsnprintf` + mutex + **每行 fflush**；所有调用点都有次数上限（12/16），
  不进热路径。但 `fflush` 比 `godot::print` 慢，若将来要高频诊断得加缓冲。
- 编译期的东西（stat 族表、预算校验、route 展开）不在运行时路径上。

**未做基准测量**——以上都是复杂度分析与「路径是否被执行」的推断，不是实测数字。
