## 1. 我发现了什么

排查「tag_build_ms 从 35.66 涨到 92.84」时，发现：

```
Id      : 139000
Process : python
StartTime: 2026/10/24 11:46:46      ← 三天前
CPU     : 69280.42 秒（≈19 小时 CPU 时间）
```

这是我早先 `git fsck --lost-found --no-reflogs` 后台任务的残留。它一直在跑。

**已终止。**

## 3. 后果：此前多轮的性能数字不可信

| 轮次 | 当时报告 | 可信度 |
|---|---|---|
| M4-16 | `rebuild_ms` 3.52 / 10.26 ms | 读错字段（已作废） |
| M4-17 | `materialise` 0.4328 / 1.2833 ms | **可能被僵尸进程放大** |
| M4-19 | 分片后 0.2305 / 0.5878 ms | **同上** |
| M4-22 | `tag_build` 12.94 → 13.30 / 34.92 → 35.66 | **同上** |

**这些数字的方向（分片后更快）大概率成立，但绝对值都不可信。**

## 4. 本项目自己的测量纪律

方案 §14.4 要求重复测量与报分位数。我在 M2 阶段记录过：

> 单次读数在共享机器上有 1.69×–1.81× 的离散，足以翻转一个 pass/fail 判定。

而今天多次出现的 `spread = 1.70× ~ 2.34×` **正好落在这个区间**。

**在此之上宣布「6400 格 0.5878 ms，门槛 PASS」是不严谨的。**

## 5. 我现在的判断

### 5.1 仍然成立的

| 结论 | 依据 |
|---|---|
| 分片真实生效 | `K: the job really took multiple steps`（确定性断言，与机器无关）|
| 分片结果与单发一致 | `K: the SAME cell count survives the split` 等 5 条 |
| `front cells=6400`、`instances=0` | 计数断言，不是计时 |
| 全回归 17/17 | 功能断言 |
| `tag_declared == tag_active == 296` | 计数 |

### 5.2 不成立的

| 结论 | 问题 |
|---|---|
| 「6400 格 ≤1 ms 门槛 PASS」 | 计时不可信 |
| 「分片把 1.28 ms 降到 0.59 ms」 | 两个绝对值都不可信 |
| 「active-tag 过滤零收益」 | 差异在噪声内，无法判定 |
| 「tag_ids 协议改动导致 2.6× 回归」 | **这个 92.84 ms 极可能是机器噪声** |

## 6. 本轮的实际交付

| 项 | 状态 |
|---|---|
| 僵尸进程 | **已终止**（这是一处真实的修复）|
| `tag_ids` 消费者协议 | 实现完成、构建通过、功能未回归 |
| `tag_declared` / `tag_active` / `tag_consumed` 计数器 | 已导出 |
| 性能结论 | **全部降级为「不可信，需在干净机器上重测」** |

## 7. 下一步（诚实版）

1. **不要在污染机器上继续调性能。** 功能工作可以继续，性能结论必须标记为待测。
2. 若要在本机继续，先建立**校准基线**：对一段固定计算跑 N 次，记录 p50 与 spread；spread > 1.5× 时拒绝采信任何差异。
3. `tag_ids` 的**功能正确性**仍需验证（`consumed` 目前为 0，因为该夹具不经 ideology 的 publisher）。

## 8. 教训

**我连续多轮用单机单次读数支撑门槛判定，而这台机器一直在跑一个三天前的僵尸进程。**

方案 §14.4 的测量纪律写在文档里，我读了，但没有执行「先验证测量环境」。

在宣布任何性能门槛 PASS 之前，**必须先证明这台机器能给出可重复的数字**。
