# 高负载一致性：先复现，再读完整流程

本轮顺序由用户确定：先写目标行为测试，保留原实现的失败证据，再沿完整输入、计算、提交、发布及保存路径读代码定位。不能先改计算实现，再用通过的测试倒推问题已解决。未复现的项目如实标记，不制造失败、不放宽比较，也不靠增加等待或重试绕过问题。

## 三个目标

| 目标 | 输入与观察 | 失败条件 |
|---|---|---|
| 正式计算不随机器忙闲改变 | 正式开局，同一种子、30日、无玩家操作，保留正式经济周期选择；逐日比较八个已有域摘要、完整经济摘要及人口/市场原始值 | 任一日期、字段或结果不同；缺日、错误、泄漏也单独记失败 |
| 同一命令在同一天生效 | 固定的13日非空操作表，包含未来日期的国家改名与军事目标；复用原回放夹具固定周期以单独检查命令边界 | 完整操作、回执或逐日状态不同，不只比较终值 |
| 保存后继续与不中断运行一致 | 同一操作表第5日保存，独立进程恢复，比较第6至13日；保存操作本身也不能改后续结果 | 任一已保存继续状态、逐日域、完整经济或表外状态不同 |

最初取证时第一项保留正式计算周期，后两项固定周期以隔离原因。改后检查器也让命令与存档走正式周期，并延长到35日以跨过30日投资边界；保留原13日失败证据。全部使用同一份源码、目录、原生库；已有断言和分片上限保持不变。

## 负载与证据

每个参考过程不启动自有压力进程；压力过程启动7个只做CPU计算的独立进程。机器上的其他任务不停止，报告记录现有进程负载，因此“参考”不冒充完全空闲。压力进程先报告就绪，直到对应Godot进程退出才停止；输出实际CPU时间和完成工作量，未真正工作的负载不算有效覆盖。

每个目标有一次参考和两次有压观察，不因失败自动重跑或替换样本。失败后保留完整输出、首次差异、原始逐日结果、已有阶段追踪、保存文件、源码与库指纹。未到达测试目标的启动或夹具错误与业务结果分叉分开报告。

检查器入口为 `tools/ci/check_runtime_load_consistency.py`，正式周期夹具为 `tests/runtime/runtime_load_daily_test.gd`，命令与存档复用 `tests/runtime/committed_view_replay_test.gd`。不安装或修改黄金基线。

## 根因分析范围

得到失败证据后才审查实现：正式入口与日历 → 环境输入与命令归日 → 各模块实际状态所有者 → 经济周期和跨模块请求 → 提交与显示副本 → 保存与恢复所需的继续状态。区分测试观察错误、真实计算时序问题和存档遗漏；先写完整因果链，再决定是否需要改实现。

运行结果见 `docs/architecture/feature-status.md` 的“高负载目标测试与计算规则审查（2026-11-15）”。此前部分执行模式下规则更新未进入经济的记录仍待核查，不把它冒充本轮已复现的问题。

## 已确认的设计方向

用户选择：逐日结果一致是第一优先级，同时尽量保持选定的推进速度。生产、消费和价格按固定游戏日推进；建设规划与投资可以保留较慢的固定周期。时间测量只能用于安排工作和诊断，不能改变下一天的业务规则。

这并不承诺无限高负载仍能原速运行。若目标每秒推进10日，机器长期平均必须在100毫秒内算完一日。用户指出旧版追帧可能一直追不上，因此不采用“积累现实时间欠账、恢复后补齐”的建议：过载时实际少推进，恢复后回到目标速度，不补回卡顿期间未推进的游戏时间。不能让显示日历先走而把未完成的交易、命令和存档留在过去。

### 从输入到提交的改造边界

1. **冻结输入与命令日期。** 第D日只用确定的环境、国家规则与已封好的命令表。同日续算沿用同一输入和请求身份。区分“尽快执行的玩家操作”和“明确指定未来日期的操作”；后者不能被统一改到最早可执行日，回执必须报告实际安排的日期。
2. **逐日经济规则。** `economy_runtime_cadence.cpp` 的实测耗时不得再选择市场结算天数。每天的有效地块、生产、消费和价格更新由游戏状态决定；补算多天必须逐日推进，不能直接把需求和生产乘天数。开局第一次结算的起点也必须明确，不能靠 `last=-1` 意外多算一天。
3. **固定慢速规则。** 建设规划、投资评估的周期来自内容配置，日期和游标属于模拟状态。当前 `lock_plan_cycle` / `lock_investment_cycle` 同样使用实测耗时，需要一起拆开；不能只锁住市场而留下另外两条负载入口。
4. **安排工作而不改变结果。** 沿用单一状态所有者，切片只保存游标。先削减重复扫描、复用输入完全相同的派生结果；只有写入范围互不重叠的计算才能并行，结果按固定地块/对象顺序合并，请求号和随机数的取得顺序也必须固定。共享市场、国库和分配优先级不能随线程完成顺序改变。
5. **完成后再发布，不累积追赶目标。** 发布的是同一游戏日的完整结果。第D日完成前只继续该日，不因现实时间流逝不断追加D+1、D+2的欠账；完成后安排下一日。调度不能清掉未完成的业务，暂停/保存/退出仍可被处理。画面可以继续响应并显示最近完成的一天，但不能把旧数据标成新日期。恢复性能后回到选定速度，不为历史卡顿加速补日。
6. **保存继续状态。** 保存同一天的真实状态、命令表、固定周期与后续游标；恢复后逐日结果必须与不中断运行相同。现有ECP2已经保存周期耗时估计，保存这些值本身无法消除下一次机器测量带来的分叉。先定位第13日完整经济摘要差异，不能删除比较字段或重写基线。

### 计算方式本身的审查

- **已确认不是纯性能优化：** 改市场周期会改变结算地块。`cell % N` 与当天周期位置决定是否执行；周期从1变成3或5，会跳过某些地块当天的生产与消费。本轮第2日已看到真实收支和库存不同。
- **明确存在近似，是否可接受取决于玩法：** `economy_runtime_market.cpp` 用 `_epoch_days` 扩大本轮需求；`economy_runtime_building_production.cpp` 也按该天数累计产出，并把供需平滑系数近似为 `min(1, daily_alpha * days)`。即使输入恒定，逐日平滑5次的系数也是 `1-(1-alpha)^5`，并不等于 `5*alpha`；库存、价格和资金还会随日变化。不能把账目平衡当成这种近似无误差的证明。用户已选择逐日一致，因此日常计算不应依赖这些多日近似来提速。
- **静态疑点，未在本轮触发：** `workset_elapsed_days` 取参与地块未结算天数的最小值，许多需求/生产路径仍用统一的 `_epoch_days`；逐格天数只进入部分消费者。已有 `epoch_elapsed_days_lost` 监测。本轮30日三次运行该计数均为0，因此不能宣称已复现丢失天数。

### 实施与验收顺序

先完成结算规则与时间测量的分离，再处理命令日期语义与存档差异；每项分别保留原始失败证据。禁止把测试的 `inject_economy_cadence_timing(0,0,0)` 当成正式修复。

三处实现已改写，验证结果见 feature-status。改后用新增的生产周期测试比较每个游戏日；命令和存档目标保留全部断言。固定周期的旧回放仅作为受控检查，不能代替正式路径验收。正确性通过后再比较相同世界、相同完成日数的速度与最慢日耗时，保持原有性能门槛；多线程数、机器忙闲与保存/恢复都不得改变结果。

### 避免追赶长期停不下来

已核对当前实现，不能把它描述成所有路径都无限积累时间债：`WorldClock._process` 已在
一帧结束时丢弃没有安排的整数日，只保留不足一天的小数；完整Climate ACTIVE的worker
由环境输入驱动，每轮目标为一天。非Climate驱动分支仍有最多100日的时间债和每批8日
追赶，它属于另一条执行路径。现有规则能限制积压，并不自动证明日历、输入生产者和
实际提交进度完全一致。

本方案进一步把“已完成的日”作为日期与下一次工作安排的共同依据，不靠不断增大队列、
重试次数或超时实现恢复。验收应在同一正式会话中经历“正常→持续过载→恢复”，检查
未完成日不不断增长、已安排日不丢失/重算、恢复后不出现补日冲刺，同时与参考逐日状态
一致。整局加压测试仍手动逐日驱动宿主；另有真实 `WorldClock` 的受控帧输入检查，
覆盖正常→长帧→100次等待→解除等待→正常，7项通过。它验证不产生补日冲刺，
**不等同于图形客户端在持续高负载下的完整长时间验证**。


日志目录必须是仓库外的新目录。可用 `--goals production_daily` 只查正式周期，或 `--goals command_days save_continuation` 查命令与存档。保存目标需要不中断的命令运行作为参考。每个阶段保留错误与结果；即使最后一天相同，中间任一天不同也失败。负载进程必须覆盖整个Godot过程，并在过程内留下实际CPU工作记录。


## 读档差异的逐字段归因

先保留原库与源码，再仅加入散列输入诊断构建。两个旧规则过程的第13日共23093个标量
散列输入，仅三项不同：地块247的三个职业动员行 `flags`，原运行1、冷恢复0。
完整散列验证未报告缓存散列错误。因果链为：冷启动跳过bootstrap → PKCN解码没有重建
`_starting_country_slot`（仍为-1）→ 经济冻结国家输入得到-1 → 首次出现动员行时玩家位变0，
后续阶段变化将走AI自动处理。开局两条路径都分配槽位0，存档已有且保持国家槽位顺序，
因此修复是恢复派生身份，不需要增添第二份玩家归属或改变PKCN格式。
新增冷恢复身份测试在旧库13检查中失败1项，证明普通暖恢复会掩盖这个问题。
诊断证据位于 `/tmp/keynes-consistency-fixes-20261115/diagnostic-{original,resume}`；临时逐字段
输出只在诊断构建使用，已从交付代码移除。

延长到35日后发现第二处读档遗漏，已先保留两次有压恢复的失败记录：原运行第31日
`season_ran=1`、基础湿度摘要变化，恢复过程均为0且摘要保持旧值。`SeasonRefreshSystem`
用 `should_run` 调用次数累计30日；冷重建清零且没有保存该计数。调度器的预算门又在
`should_run` 之前，因此该计数本身也不能代表游戏日。修复把普通Climate ACTIVE的到期
判断移到既有输入采集边界，按输入日31、61……执行，复用CLM2已保存的完成日期去重，
不增加另一份计数或改变存档格式。完整计算和发布仍调用原刷新流程；不完整刷新不发布输入。
新目标测试在旧实现269项中失败3项，覆盖刷新前后冷重建；最终270项通过，同时覆盖
重复/遗漏调度观察、同日采集重试和权威切换时完成已经开始的刷新。
证据见 `save-season-root-cause.json`、`season-target-*`。

## 提交前扩展场景归因（2026-11-16）

军事20日冷恢复在第21日暴露另一项交接遗漏：开日完整经济摘要一致，建筑生产前的
人口/市场/资源输入一致，但冻结国家商品系数75366→65536。启动时在权限授予前查询
旧Host状态，选择了显示副本作为经济读者。修复按已验证的请求权限选择后台专用读者；
地块派生层须在同一日边界单独发布，普通实例快照不包含它。实际读者目标从51项失败2项
变为全部通过，192格数值精确一致。此例说明权威摘要相等不证明消费者拿到相同输入。

另一个独立遗漏为生产销售历史：报价读取上期商人销量比例，原保存把四个历史数组当作
临时缓存。冷恢复目标确认缺失后，将四列作为PKEC64信号记录保存并加入完整状态摘要，
ECP2格式递增至63。未用这一遗漏解释前述15%产量差；两者分别有独立证据。
最终验证结果统一记录在 feature-status，原有失败证据不覆盖。
