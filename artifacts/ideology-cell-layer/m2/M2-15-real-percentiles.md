## 1. 为什么之前拿不到分位数

三次失败，每次都是不同原因：

| 轮次 | 尝试 | 失败原因 |
|---|---|---|
| M2-13 | 同一次运行内取 6 天 | 构建完成后每天版本早退，读到的是同一个冻结值 |
| M2-14 | 每天 bump 版本强制重建 | `version_probe` 五天完全相同，版本没变 |
| M2-14 | 修日戳（`_day - 1`） | 结果完全相同，日戳不是原因 |

根因是循环依赖：**要 bump 才能重建，要重建才能读取 bump**。读者在一个 epoch 内已收集完工作集，之后 bump 的行只能等下一 epoch，而下一 epoch 又会早退。

## 2. 正确做法：每次样本一个新进程

```
python Project/project-keynes/tools/ideology/measure_city_factor_runs.py \
    --cells 800 --runs 5
```

每个样本是独立进程 + 全新世界，因此**真正独立**。代价约 5 分钟/样本。

## 3. 实测分布

```
[runs] run 1: 4.717 ms over 13 slices / 800 cells
[runs] run 2: 2.848 ms over 13 slices / 800 cells
[runs] run 3: 3.510 ms over 13 slices / 800 cells
[runs] run 4: 4.516 ms over 13 slices / 800 cells
[runs] run 5: 4.805 ms over 13 slices / 800 cells

n=5  min=2.848  p50=4.516  p95=4.805  max=4.805 ms
us/cell at p50 = 5.645
spread max/min = 1.69x
```

**离散度 1.69x，采样器自己触发了警告。** 这正面回答了我一直缺的那个问题：

> 任何单次读数都可能偏差 69%。M2-12 的 14.376 ms（7.19 us/cell）与 M2-13 的 7.799 ms（3.90 us/cell）差 1.8 倍，正是这个分布的两个尾巴。

## 4. §14.3 门禁判定

| 量 | p50 | p95 |
|---|---:|---:|
| 每片 city 因子（13 片） | 0.347 ms | **0.370 ms** |

**判定：通过。** 使用 p95（而非乐观的 min）仍有 16.5% 余量。

## 5. 一个值得注意的巧合

| 来源 | 每格成本 |
|---|---:|
| M2-6 O2 微基准推算 | **6.0 us** |
| M2-15 实测 p95 | **6.01 us** |

**几乎完全一致。** 这说明 M2-6 的模型常数选得对——尽管中间经历了 M2-12（7.19 us）和 M2-13（3.90 us）两个离群读数。

按 p95 外推 6400 格：**38.4 ms / 100 片 / 每片 0.384 ms**，与 M2-6 的原始推算 38.4 ms 完全吻合。

## 8. 局限

- **只有 800 格一个规模有分布。** 6400 格仍是外推。
- **n=5 偏少**：p95 用 nearest-rank，在 n=5 时等于 max。要报真正的 p99 需要 ≥20 个样本。
- 每样本约 5 分钟，20 个样本约 100 分钟。
- 采样器读的是日志最后一行 `epoch_ms`；若某次运行产生多个完成的构建，只取最后一个。
- 未区分冷建与热更新（§14.1 要求分开统计）。
- debug DLL。
