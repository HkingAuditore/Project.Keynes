## 木材(timber)"荒谬低值"真相与修复 —— moisture_opt 越界（已落盘 tres）
- 用户截图：第2年热带雨林(丘陵,气候"酷热·干燥")cell 木材仅 1563 且 delta −13.34 持续下跌，重启多次无效。
- **根因（本轮读 C++ 源码定位）**：timber `climate_moisture_opt` 被设成 0.91（上一轮从调优器选的），但**世界湿度天花板 land moist p90≈0.56**，0.91 是任何陆地格都够不到的越界值 → 全体 moisture_fit 偏低，"干燥"雨林格(moist~0.30)climate_fit 仅 0.12 落进 acute_stress 区 → Beverton-Holt 收敛值仅几百。
- **纠正我此前的连环误判**：前几轮拿 `map_generator.gd` GDScript fallback 公式模拟得"雨林稳82万"，那是 fit=1.0 的**理论上限格**，真实地图无此格（moist 到不了0.91）。真实运行是 **C++ `world_ext_resource.cpp:174-209` `natres_step_scalar_ecology_dt`**，GDScript fallback 正常游戏不执行。用户重启一直有效，是参数本身选错，与缓存/重启无关。
- **关键公式事实（C++ 权威）**：`capacity = ecology_capacity × runtime_fit`（C++ 侧**不乘** quantity_scale）；但 `build_pass_knobs`(resource_profile_registry.gd:211/213/210) 在传入前已把 ecology_capacity/immigration/decay_stress **预乘 quantity_scale=100**（growth_rate/mort/stress_mort 不乘）→ C++ 实收 cap=10000×100=1e6。故 capacity≈1e6×runtime_fit，与初始 bootstrap(×CELL_AREA_RESOURCE_SCALE=100)量级对齐。
- **修复**：`timber.tres` `climate_moisture_opt 0.91→0.55`(贴天花板)、`climate_moisture_tol 0.71→0.35`(陡峭梯度,草原≈无木材)。用户经 AskUserQuestion 确认这两项方向。
- **验证（C++ 公式精确模拟）**：改后热带雨林 76万→稳84万（初始贴承载量,不再暴跌）;温带林59万;干林45万;针叶林29万;稀树草原728;沙漠88。符合 Whittaker 分布。
- 待用户本地重启验证。若嫌雨林内部干湿差距大(84万 vs 45万)可把 tol 0.35→0.40 折中。temp_opt/temp_tol 保持 0.77/0.80。

### 缩产机制优化方案（用户问"极端缩产太不合理，如何优化"，已产出方案，未改代码）
源码定位（economy_runtime.cpp）：
- L3638-3646 库存过剩收缩：`inventory_absorption_q16 = target/stock`（target≈0、stock 巨大时 → 系数≈0）。
- L3648-3669 util 更新：`util += (min(target_util, inventory_target_util) - util) * supply_price_elasticity`；target_util = util*sell_through。**问题：target_util 与 inventory_target_util 都是"util 的比例"，连乘会指数级坍缩**。
- L3681-3684 下限 `probe_floor = 1/32(≈3.1%)`（普通品）或 1/6（cycle_flow/survival_food）。这就是观测到的 3% 底。
- L4170-4176 `planned_owner_demand = count*owner_slots*util`；util=3% → owner 岗位直接砍到 3%，无缓冲，失业立即产生。

已识别的 4 个不合理点 + 建议（按性价比排序）：
1. **收缩太快无阻尼**：单周期就能从 100%→3%。建议给下调加"每周期最大降幅"（如每周期最多降 30%），或降 elasticity 对"下调方向"的响应速度（上调快、下调慢，非对称阻尼）。
2. **owner=生计，缩产=失业无缓冲**：util 直接线性决定 owner 岗位。建议 owner 岗位与 util 解耦——保留"最小在岗 owner"（如满编的 25-50%）维持生计，util 只调产量/雇员，owner 缓慢退出（每周期最多退 N 人）。这是最贴合"人口不该瞬间失业"诉求的改法。
3. **probe_floor 对滞销品仍偏高**：1/32 让 flint 这种零需求品永久空转小产。可让 probe_floor 依"近期是否有真实成交"再降一档（如无成交连续 K 周期 → floor→0，配合 loss 状态机停业）。但要谨慎：这会让停业更快，与诉求1相反，需权衡。
4. **内容层根因**：flint/cloth 在本格无下游、trade=0 无法出口。**最省事的修复其实在内容层**——别在无下游格子放纯生产建筑，或给这些商品配下游/开贸易。runtime 逻辑本身"正确响应滞销"。

优先级建议：内容层修复(4) 治本且零风险 > owner 退出缓冲(2) 最贴诉求 > 非对称阻尼(1)。改 native 属 authority#2 热循环，需 rebuild + N=1 对照 + 守恒/hash 验证，本环境不能验证，故仅出方案。
- 产出：缩产机制对比图（show_widget: 缩产机制优化对比）。
- 结论：第一波失业不是破产、不是资源枯竭，而是库存过剩/本地需求不足触发的自动缩产；但把 owner 自雇岗位直接按开工率裁掉，会在封闭单格中放大为失业→现金流失→饥荒正反馈。

### 就业「每周期清零重填」机制解答（回答用户「为什么每一tick都要重新填充岗位」）
- 澄清：不是每 tick，而是每个 market epoch 的 `BUILDING_EMPLOYMENT` 阶段（调度序列 LEDGER→TRADE_DISPATCH→BUILDING_EMPLOYMENT→BUILDING_PRODUCTION，economy_runtime.cpp:8589）触发一次 `run_building_employment_cell`(L4149)。
- 清零重建代码：L4190 先把该 cell 所有 cohort 的 `owner_employed`/`employee_employed` 清零 → 把所有建筑 `filled_owner`/`_building_employee_filled` 清零 → L4203-4237 按 `planned_owner_demand=count×slots×planned_utilization_q16/Q16_ONE`(L4170) 用前缀和按比例重新摊派。
- 用无状态清零重建而非增量的四个原因：① 确定性 hash 硬约束（纯函数：输入=population+util+count 唯一决定输出，与上周期填了谁无关，避免路径依赖漂移）；② 三个输入量每周期都变（population 出生死亡迁移、util 被缩产公式重算、signature/profession 归属变），无从增量；③ 前缀和按比例摊派需全局视角（total_fill=min(pop,total_demand) 再按比例切各建筑）；④ 避免幽灵在岗/账目错位（count 归零或 building_available 变 false 时残留 filled_owner 会污染 household_market 收入与守恒审计）。
- **与失业问题的关联（关键）**：owner 岗位数 = pop×slots×util 且每周期从零重算 → util 100%→3% 坍缩后，下一 employment 周期立刻清空、只按 3% 重填、97% 当场失业，**零跨周期缓冲**。这是「无缓冲失业」的实现层根因。
- 优化方案②落地点即在此函数：引入跨周期「上周期在岗数」作为受控确定性输入（`max(planned_demand, min_retained_owner)` 或每周期退出上限 N），仍保持纯函数/hash 确定，而非打破清零重建范式。需新增 per-group 状态字段（如 `prev_filled_owner`）。

## 失业池增量就业重构 —— 核心 C++ 实现已全部落地（2026-07-16，待用户本地 rebuild 验证）

### 三个决定性架构决策（本次 3 轮 AskUserQuestion 拍板）
1. **slot 语义 = A1 纯粹迁移**：`profession|eth` slot 内的人全部在岗（`owner_employed + employee_employed == population`，非 merchant/非 unemployed slot 的硬不变量），任何未被雇佣者立即迁往 `unemployed|eth` 池。unemployed 是唯一失业蓄水池，裁员=迁出、招人=迁回。owner/employee_employed 降级为「slot 内业主/雇员的拆分标注」。
2. **实现结构 = 统一净增量迁移**（非三显式阶段）：每 slot 算 desired_working = owner目标 + employee目标；population>desired 部分迁池、<desired 从池招回。数学等价「消失清理+建筑驱动裁员+优先级招人」三阶段合并，A1 不变量天然成立，owner/employee 在 slot 内竞争 population，无需阶段间传 slot 剩余容量。
3. **Task #6 = 保持派生量，不升 schema**：A1 下失业者是一等 cohort（已随 population section 进 save/hash/restore），`_unemployed_population` 是纯派生量（=Σ unemployed cohort population），restore 后首个 employment tick 重算即可 → **不升 SCHEMA_VERSION（保持 12）**、不进 binary save/hash（避免冗余+时序脆弱）。旧 v12 档 restore 后首周期自愈。
