④ 气候/天气束内部（⚠ 数据存疑）

埋点告警：bd_climate_* 与 bd_weather_* 两列族逐字段数值完全相同（compute / climate / weather / wind / advance 等全部一致，连 p95、max、非零计数都一致）。这说明天气束的计时器在记录层被气候束的值覆盖（aliasing）。在修复前，气候 vs 天气的真实拆分不可信，下方仅展示"束内部"相对构成，且代表同一份数据。

在当前（疑似重叠）数据中，束内最重的子阶段是 compute（均值 1.14ms、p95 2.94ms、最大 6.22ms），其次为 climate / weather / wind / advance 阶段。注意子阶段之和远超束 total，说明各子阶段是"该帧所跑的那一段"的耗时，而非整帧累计。

⑤ 进一步优化空间

A. 主攻 native_daily_sim（占 39%）
这是单一最大 recurring 成本。其最大切片 stage 多为物理传递：phys_psi_init / phys_upwelling / phys_slp / phys_wind / wind_air / daily_wind_prepass。可方向：① 离玩家/离大陆远处用更粗网格或跳步（LOD）；② 输入未变化时跳过整段重算；③ 进一步把单段切成更小切片以压低 p95。
B. 次攻 ocean_currents（占 25%）
第二大成本，最大切片 stage 为 ocean_water / phys_wind / phys_slp。与 A 同属物理求解器，可共用 LOD / 跳步 / 缓存策略。两者合计 64%，是性价比最高的两个优化点。
C. 压住尖峰而非均值
越界只发生在尾部：enum_atlas_upload 最大 7.5ms（仅 61/491 ticks，但属事件型 GPU atlas 重建尖峰）、native_daily_sim 最大 7.79ms、fast_ms 最大 12ms。建议把 atlas 重建/上传拆成更细 chunk 或挪到独立线程/延迟提交，避免单帧内一次性 7.5ms 卡顿。
D. 先修埋点 aliasing（阻塞性）
气候/天气计时器重叠，导致无法判断真实热点在气候还是天气、也无法验证束内优化效果。修好 recorder 让 bd_weather_* 读取自身计时器后，再决定是否对束内部（compute 等）做微优化，否则优化目标会是盲的。
E. 余量利用策略
当前 p95 5.9ms 相对 8ms 预算有 ~2ms 余量。若目标是"更丰富仿真"，可在该余量内加内容；若目标是"绝对稳 60 帧"，则应把预算阈值与切片更激进地贴合 p95，并以上限（最大/尖峰）为守门指标。
附注：t_render（均值 0.10ms）与 t_ui（0.38ms）占比极小，渲染与 UI 不是瓶颈，无需投入。
