# M4-16 §14.3 性能门禁：rollout 全开下的实测（n=7）

| 项目 | 内容 |
|---|---|
| 里程碑 | [M4](../22-cell-program-cap-removal-plan-v3.md) §14.3 |
| 日期 | 2026-10-27，Asia/Hong_Kong |
| 状态 | rollout = `Sources`（kind 12/14/15/16，265 program）|
| 结果 | **city_factor 门槛 PASS；`rebuild_ms` 在 6400 格为 10.26 ms，超出 1 ms** |

## 1. 实测数据（n=7 中位数，debug DLL）

| 格数 | covered | `city_factor_ms` | `rebuild_ms` | `tag_build_ms` |
|---:|---:|---:|---:|---:|
| 2400（生产默认） | 4800 | **0.0023** | **3.5153** | 15.31 |
| 6400（单国全国） | 12800 | **0.0021** | **10.2626** | 46.79 |

spread：city 1.25×/1.68×、rebuild 1.24×/1.90×、tag 1.35×/2.26×。

## 2. 三条结论

### 2.1 `city_factor` 门槛 PASS，但这是「无卡日」的数字

`0.0023 / 0.0021 ms` 远低于 1 ms。**但这不是 §14.3 担心的那条成本。**

夹具的顺序是「跑完经济日 → 装卡」，所以这一天的 city factor 里**没有派生贡献**。真正叠加了派生成本的，是**装卡后的下一天**。

**前一次的读数 `0.4127 / 0.9665 ms`** 是 bootstrap 那一遍（有卡之前），也不是稳态。两个读数都不能代表「派生成本叠加在 city factor 上」的情形。

### 2.2 `rebuild_ms` 线性，但绝对值超标

```
2400 格：3.5153 ms / 4800 covered = 0.732 us/cell
6400 格：10.2626 ms / 12800 covered = 0.802 us/cell
```

**按覆盖格线性**（0.732 → 0.802，比值 1.10），这是健康的行为——说明没有隐藏的 O(n²)。

但 §14.3 的硬条件是**「主线程单次派生 native slice 目标 ≤1 ms」**，而这里 2400 格就已经 3.52 ms、6400 格 10.26 ms。

**这是本迁移自身引入的成本，不是既有基线。** 与 §14.3 注 1 说的「6400 格基线本身已超 1 ms」是两回事：那条说的是 `refresh_city_modifier_factors`（既有），这条说的是新增的派生物化。

### 2.3 `tag_build_ms` 近似线性，但绝对值很大

```
2400 → 15.31 ms，6400 → 46.79 ms
2.85x 时间 / 2.67x 格数
```

**46.79 ms 的 tag 重建落在单次 slice 里是不可接受的。** 这直接印证了 §15.6 里「per-tag changed words」这项 M4 任务的必要性——当前是**每次全量重建**，没有增量。

## 3. 与方案记录的对照

| 项 | 方案记录（M1，rollout OFF） | 本次（rollout Sources） |
|---|---|---|
| `epoch_begin_city_factor_ms` 2400 | 0.465 ms | 0.0023 ms（无卡日） |
| `epoch_begin_city_factor_ms` 6400 | 1.264 ms | 0.0021 ms（无卡日） |
| `cell_layer_rebuild_ms` | 未测 | **3.52 / 10.26 ms** |
| `tag_snapshot_build_ms` | 未测 | **15.31 / 46.79 ms** |

**方案里没有派生物化与 tag 重建的成本记录，因为那时 rollout 是 OFF，这两项根本不运行。** 本次是第一次测到它们的真实量级。

## 4. 门槛判定

| 门槛 | 判定 | 依据 |
|---|---|---|
| §14.3「主线程单次派生 native slice ≤1 ms」 | **FAIL** | `rebuild_ms` 3.52 / 10.26 ms |
| §14.3「派生路径 `truncated=0`」 | **PASS** | 全 fixture `truncated=0` |
| §14.3「逐格 Effect 实例为 0」 | **PASS** | B7/B8/B10 均 `instances=0` |
| §14.3「B5 物化/安装/版本 bump 增量为 0」 | 未测 | 需 B5 夹具 |
| §14.3「不再有随 S 增长的整图 seen 清零」 | **PASS** | `own_tag_rejected=0`，无整图清零 |

## 5. 必须如实说的一句话

**我把「≤1 ms」这条门槛测成了 FAIL。**

`rebuild_ms` 在 2400 格（生产默认地图）就已经 3.5 ms，是门槛的 3.5 倍。这不是测量口径问题，是本迁移新增的物化成本本身超预算。

方案 §14.3 要求「超出必须继续分片，不能只报告平均值」——**分片物化正是 §15.3 列为必要项的工作，而它还没有做。**

## 6. 局限

- 夹具的顺序（先跑日、后装卡）意味着测到的是**无卡日**，不是「派生成本叠加在 city factor 上」的最坏情形。
- 未测峰值内存（§14.3 要求）。
- 未测 B5（无变化日）的零增量。
- 单机、debug DLL，未测 release。
