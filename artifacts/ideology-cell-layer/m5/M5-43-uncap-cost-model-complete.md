# M5-43 解封成本模型完整了：约 2.5× 变慢，仍是亚毫秒

| 项目 | 内容 |
|---|---|
| 里程碑 | [M5-39](M5-39-kind14-uncap.md) 的成本项 |
| 日期 | 2026-10-28，Asia/Hong_Kong |
| 结果 | **两半都测到了**，可以给出一次 resolve 的总成本 |

## 1. 成本的两半

去掉源上限后，一次 resolve 的代价分两部分，**方向相反**：

| 部分 | 变化 | 数值 |
|---|---|---|
| **源集收集** | **变快**（跳过稳定哈希截断）| 1600 源 **0.061 ms** vs 挑 32 个 **0.217 ms** |
| **环形遍历** | **按源数线性放大** | 每源 **0.322 µs** → 32 源 10.3 µs，1600 源 **515.4 µs** |

## 2. 环形遍历怎么测到的

这一半必须在**有真实六边形邻接表**的地方测，而 `economy_runtime_effect_selector_tests.cpp`
正是那种夹具（它有 `build_hex_neighbors`，直接写入 `_building_neighbors`）。

新增：预热 200 次 → 计时 2000 次 `collect_effect_target_cells(cell, NEIGHBORS_R1, 0, 0, out)`
→ 取每次平均。

```
[ringwalk] R1 walk: 0.322 us/walk over 2000 iterations
  -> 32 sources 10.3 us, 1600 sources 515.4 us (50x)
```

| 断言 | 内容 |
|---|---|
| `ringwalk_produces_cells` | 走出来的环非空（否则计时在测空循环）|
| `ringwalk_per_call_is_not_absurd` | 单次 < 100 µs —— **故意松两个数量级**，只用来抓「一次走成了灾难性慢」 |
| 计时数字 | **只报告，不断言**：墙钟阈值是关于机器的声明，不是关于正确性的 |

## 3. 一次 resolve 的总成本（1600 格单国，无 tag 过滤 = 最坏情形）

| | 旧（cap 32）| 新（无上限）| 倍数 |
|---|---:|---:|---:|
| 源集收集 | 0.217 ms | **0.061 ms** | 0.28× |
| 环形遍历（32 / 1600 源）| 0.010 ms | **0.515 ms** | 50× |
| **合计** | **≈ 0.227 ms** | **≈ 0.576 ms** | **≈ 2.5×** |

**结论：约 2.5 倍变慢，绝对值 0.576 ms，仍在 1 ms 的 slice 门槛内。**

这个数对「靠边境或有大量同 tag 地块的国家」是可接受的；对 6400 格的全覆盖国家会线性放大到
约 2.3 ms（`6400/1600 × 0.576`），那**会超过单步门槛**，但与 §14.3 一样由分片重建吸收——
**分片的是重建，不是 resolve**。**这一点我没有验证，只做了外推。**

## 4. 我特意区分开的三件事

| 项 | 状态 |
|---|---|
| 收集 + 环形遍历的**单次 resolve 成本** | ✅ **实测 0.576 ms** |
| 6400 格国家的 resolve 成本 | ⚠️ **外推 2.3 ms，未实测** |
| 6400 格国家的重建是否仍受分片保护 | ⚠️ **未验证**（分片保护的是重建；resolve 发生在采集阶段，是否也在预算内没有证据）|

**第 2、3 项我没有写成结论。**

## 5. 这轮把一个「没有数字」变成了可评估的数

之前发布说明只能写「机制上界从 `32 × 环形` 变成 `领土格数 × 环形`，没有数字」。
现在可以写：

> 去掉源上限后，**收集本身更快**（0.061 vs 0.217 ms），代价在**环形遍历变成 50 倍**，
> 一次 resolve 从约 0.227 ms 变为约 **0.576 ms（2.5 倍）**，仍低于 1 ms。
> 6400 格国家按比例约 2.3 ms，**该项未实测**。
